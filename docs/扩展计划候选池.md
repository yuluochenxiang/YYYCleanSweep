> **本文用途**：把已讨论过的、尚未实现的扩展方向用同一套模板摆平，便于排序决策。
> **不含代码**，每项只写到「能判断做不做」的程度。
>
> 相似图片去重已单独成文（见 `扩展计划_相似图片去重.md`），本文末尾仍将其列为候选之一，

## 一、速览对比表

工作量与感知强度为**相对量级**（小/中/大），非时间估算。

| 候选 | 包体影响 | 工作量 | 感知强度 | 主要复用 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| **A** 长期未访问文件 | 无 | 小 | 中 | `scanner.dir_size` | atime 可能被系统关闭，必须兜底 |
| **B** 空间变化快照 | 无 | 中 | **高** | `core/cache.py` | 快照数据增长，需滚动清理 |
| **C** 重复文件夹检测 | 无 | 中 | 中 | `dirstat.DirTree` | 大量误报（node_modules 等）需可调阈值 |
| **D** 清理方案导出 .bat | 无 | 小 | 中高 | `_selected_plan()` | **生成的 bat 必须 GBK 无 BOM** |
| **E** 命令行模式 | 无 | 中 | 低（自动化价值高） | `main.py` | 无头环境需 offscreen |
| **F** 空间低于阈值提醒 | 无 | 小 | 低中 | — | 不宜做后台常驻 |
| **G** 自定义规则编辑器 | 无 | 大 | 中 | `rules._external_rules_dir` | 写坏规则会导致程序异常 |
| **H** 压缩包内容清单 | 无 | 小 | 低 | 标准库 `zipfile` | 仅支持 zip/tar，rar/7z 无解 |
| **I** 相似图片去重 | 无 | 大 | 高 | `core/thumbs.py` | 误判风险（见独立文档） |

> 全部候选**均不引入第三方依赖**，包体维持现状（约 49 MB）。
> 这条是本项目一贯的红线：一旦引入 Pillow / numpy / opencv，包体会立刻涨 3~30 MB。

## 二、候选详述

### 候选 A：长期未访问文件

**一句话**：扫描时顺手记下「最后一次被打开」的时间，新增一列 + 快捷筛选。

**解决的痛点**
现在只能看到**修改时间**（`mtime`），但 mtime 会被复制、备份、迁移整批改写，
无法反映「这个东西我到底有没有用过」。磁盘清理最经典的抓手其实是「几年没碰过的东西」。

**技术方案**
`core/scanner.py` 的 `dir_size()` 目前在遍历文件时顺便记录最新的 `st_mtime`
（供 v3.24 的「智能推荐」算分用，见 `core/scanner.py:59`、`_match_size` 的 `:102`）。
`os.stat()` 的结果里已经包含 `st_atime`，**几乎零成本**就能一并记录下来。

- 返回结构在 `newest` 之外增加 `accessed`（子树内所有文件的最近访问时间）
- `core/cache.py` 的 `put_dir(path, size, count, newest)` 需增加对应字段
  （注意：已有数据库需要**做字段迁移**，不能破坏老版本的数据）
- 存储层新增列要兼顾 `_ensure_schema()` 的既有写法

**UI 落点**
目录分析页树表新增「最后访问」列；顶部筛选区增加快捷项「1 年没打开过 / 3 年没打开过」。

**⚠️ 已知坑（必须在实现时处理）**
1. **Windows 可能关闭 atime 更新**（NTFS `NtfsDisableLastAccessUpdate` 策略）。
   代码必须做**兜底**：atime 取不到、或 atime 早于 mtime 时，回退用 mtime，绝不显示空白列。
2. **atime 精度粗**：NTFS 下约 1 小时粒度，FAT 更大。不能拿来判定「刚刚访问过」。
3. 扫描器自身读取文件**会不会改动 atime**：纯粹的 `stat` 不会，但如果以后加了任何读内容的行为就会污染结果。

**开放问题**：是否需要「按最后访问排序」的点表头能力？（现有 `HeaderSorter` 已支持数值列排序）

### 候选 B：空间变化快照对比

**一句话**：每次扫描留一份快照过一段时间后再看，直接告诉你「谁涨了」。

**解决的痛点**
最能回答「C 盘怎么又满了」的功能。当前工具能告诉你「现在谁占的多」，
但回答不了「是**谁涨**上去的」——而后者才是用户真正想问的。

**技术方案**
`core/cache.py` 已有一整套 SQLite 设施（`get_dir` / `put_dir` / `stats()` / `clear()` /
`db_file()`，多线程安全，异常静默降级）。快照可以**复用同一个 db 文件**，另开 `snapshots` 表：

```
(path, ts, size, count)
```

- 每次扫描结束落一份（需标记来源，避免缓存命中时重复写）
- 保留策略：**最近 N 份滚动**（默认 30）+ 超时淘汰，参考 `core/cache.py` 已有的
  7 天 TTL 思路（`TTL_SECONDS`）
- 「设置页」的「扫描缓存」卡片旁，增加快照的占用与「查看 / 清除」入口（参照 v3.29 定的规矩：
  缓存类信息要给单位、给路径、给「打开位置」按钮）

**UI 落点**
目录分析页顶部卡片，文案类似「相比 30 天前，Downloads 涨了 3.2 GB」并列出增长最快的前几位。

**为什么感知强度标为「高」**
这是所有候选里唯一一个**回答了新问题**（而不是把老问题换个角度呈现）的。

**⚠️ 已知坑**
1. 快照数据随时间增长，必须有滚动条数与容量上限，否则 db 会无限膨胀
2. 磁盘整理、大规模迁移会制造与真实行为无关的「增长」，需要能手动清除某段记录
3. 路径大小写 / 盘符变化（换盘、重装）会让历史对不上，需做规范化（参照 `cache._norm_key`）

### 候选 C：重复文件夹检测

**一句话**：找整棵被复制过去的目录树，而不是单个重复文件。

**解决的痛点**
项目备份的多份拷贝、多处存在的 `node_modules`、整目录复制造成的浪费。
单文件去重即使能找，也会列出成千上万个文件，用户看不过来；而按**目录**报才看得懂。

**技术方案**
`core/dirstat.py` 已有完整的 `DirTree`，`DirNode` 带 `own_size` / `own_count` /
`own_ext` / `agg_size` 等字段（见 `core/dirstat.py:22` 起的 `__slots__`）。

- **精确重复**：对每个目录算「相对路径 + 文件名 + 大小」集合的哈希（排序后喂 md5）
- **近似重复**（更有价值也更难）：文件名集合交集率 > 阈值 且 总大小差 < 阈值
  → 能抓出「同一项目的新旧两个版本」
- 比对前先用「文件数 + 总大小」分桶过滤，避免全树两两比对

**⚠️ 已知坑**
1. **node_modules / venv 会大量命中**——但这恰恰是用户想找的东西，问题在于会淹没其它结果，
   需要能单独开关或折叠
2. 近似判定的两个阈值必须暴露给用户，不能在内部写死一成不变的标准
   （这与相似去重的相似度阈值同理：多像才算重复，是主观的）
   
**开放问题**：结果按「完全相同」和「大部分相同」两类分开展示，是否足够？

### 候选 D：清理方案导出 .bat

**一句话**：把这次勾选的清理项导出成一个批处理，可拿去管理员运行或放进计划任务。

**解决的痛点**
UI 里删不动的东西（被占用的、需要提权的 pagefile 之类、系统级目录），
导出成脚本后右键「以管理员身份运行」就通了；也方便做定时清理。

**技术方案**
复用现成的选中结果 `MainWindow._selected_plan()`（返回 `[(rule_id, [paths])]`，
见 `ui/main_window.py`），生成脚本内容：

- 每个路径一条删除指令，**路径加引号**（防空格）
- 默认生成**带中文注释的版本**，让用户先看懂再执行
- 提供「直接删除 / 移到回收站」两种口径可选
- 结尾带 `pause`

**UI 落点**
靠近现有「导出配置」按钮（`ui/main_window.py:1080`）或清理按钮的下拉菜单里。

**⚠️ 已知坑（本项目踩过，务必遵守）**
> **生成的 .bat 必须是 GBK/ANSI 且不能带 UTF-8 BOM**，也不能在开头放 `chcp 65001`。
> 依据：项目长期笔记里的 *bat 铁律* —— 带 BOM 会让命令解释器第一行就解析失败；
> `chcp 65001` 会让批处理当场终止（表现就是"一闪就没"）；LF 换行同样会让批处理错乱。
> 中文注释要显示正常，就必须 GBK 无 BOM + CRLF。

这条风险看着小，实踩过，实现时必须按此走，别用 UTF-8 写出去。

### 候选 E：命令行模式

**一句话**：无界面跑一次扫描并输出结果，方便接计划任务。

**解决的痛点**
「定时自动扫一遍」这件事，图形界面天然不适合；有了命令行才能配合 Windows 计划任务。

**技术方案**
`main.py` 现有入口是标准的 `QApplication + MainWindow`。加 `argparse` 分支：

```
YYYCleanSweep.exe --scan --target C: --json out.json
YYYCleanSweep.exe --scan --target D:\Work --min-size 500MB --html report.html
```

- 无界面时走离屏：项目已有成熟经验
  （`QT_QPA_PLATFORM=offscreen`，且 `MainWindow.__init__` 有 `QTimer.singleShot(150, start_scan)`
  需在无头模式下抑制）
- 复用 v3.26 已实现的 `ui/report.py` 的 HTML 导出能力（`_build_html`）
- 约定退出码：0 正常 / 非 0 异常，便于脚本判断

**⚠️ 已知坑**
1. 命令行扫描期间不能写 GUI 配置，避免两头打架
2. 单文件版启动要解压约 113 MB 到 `%TEMP%`（v3.30 README 已写明），
   **定时任务应优先用文件夹版**
3. 感知强度标低，是因为普通用户不会用它；但对「自动化」场景它是地基（候选 F 依赖它）

### 候选 F：空间低于阈值提醒

**一句话**：启动时发现磁盘快满了就提醒一句。

**解决的痛点**
总是在「已经满了」才想起来清理，缺少提前预警。

**技术方案**
启动后检查目标盘可用空间，低于阈值（可在设置里配，默认比如 5 GB / 5%）时给提示。

**⚠️ 关键决策：不要做后台常驻**
这是一个**离线小工具**，不是杀毒软件。做成后台监控会常驻内存、违背「轻量」定位。
正确做法是**只在启动时检查一次**；
真正的「定期检查」应该交给候选 E（命令行模式）+ Windows 计划任务去组合实现。

> 也因此，**候选 F 依赖候选 E**，单独做价值有限。

### 候选 G：自定义清理规则编辑器

**一句话**：不用手改 JSON，在界面里增删改自己的清理规则。

**解决的痛点**
`rules\*.json` 目前要手动编辑，门槛高、容易写错格式，普通用户根本不敢动。

**技术方案**
`core/rules.py` 已有 `_external_rules_dir()`：**程序优先读 exe 旁的 `rules\` 目录**，
这是一个天然的用户自定义入口；写回也写那里，不动打包时嵌进去的默认规则。

- 设置页加「规则编辑」入口，用表格编辑 `clean_rules.json` / `dir_knowledge.json`
- 字段下拉必须受控：`risk` 取值来自 `RISK_ORDER`，`kind` 取值来自 `KIND_LABEL`，
  避免手填错值（这条是 v3.27 修过的教训：手写对照表必然和真实取值脱节）

**⚠️ 已知坑**
1. **写坏了程序会起不来**。必须：改前自动备份 `.bak` + 提供「恢复内置默认规则」按钮
2. JSON 保留原文件注释/顺序不现实，要接受重新序列化后的diff
3. 工作量大在「表单/校验/错误提示」这一块，不是存储和读取

**感知强度中**：对愿意自定义的用户价值很高，但属于小众需求。

### 候选 H：压缩包内容清单

**一句话**：选中一个压缩包时，右侧详情列出它里面装了什么。

**解决的痛点**
不知道某个几百 MB 的 zip 里具体是些什么，值不值得留。

**技术方案**
标准库 `zipfile` 读 `namelist()` 与每个成员的大小（`tarfile` 可顺带支持 tar/gz），
在大文件 / 目录分析页选中时，把内部 Top N 画进右侧详情面板（参照现有 TypeBars 的呈现方式）。
**不解压缩、不落盘**，只读清单。

**⚠️ 已知坑**
1. **只支持 zip / tar**：`.rar` / `.7z` 标准库搞不定，强行做要引入 `py7zr` 等依赖——碰红线，不做
2. 加密压缩包读不了密码保护的成员，需优雅降级为「无法读取」
3. 超大 zip 的清单可能很长，要截断 + 「按大小排序 Top N」

**感知强度低**，但工作量也最小，适合当作两个大功能之间的缓冲。

## 三、排序时的几个客观依据

不看实现难度，只看「做完对用户意味着什么」：

1. **唯一回答新问题的候选是 B（空间快照）**——其余都是把已有信息换个视角呈现。
2. **唯一能显著提升清理能力的候选是 I（相似去重）**——它是唯一能找出「现有算法看不见的冗余」的功能。
3. **唯一为后续自动化铺路的候选是 E（命令行）**——F 依赖它，且和 D 组合能形成
   「导出脚本 → 定时执行」的完整闭环。
4. **成本最低、可穿插做的是 D、A、H**——都工作量小、包体不变、风险可控，
   适合作为两个大功能之间的调剂。

> 排序结论由用户最终决定，以上仅供参考。
