# YYYCleanSweep 扩展方案：相似图片去重（v3.31 候选）

> 本文是**方案讨论稿**，不含代码。目标是把「靠缩略图做视觉相似去重」这件事的可行性、
> 风险边界、以及必须提供的用户开关一次性说清楚，等结论确认后再动手实现。

---

## 零、结论先行

| 议题 | 结论 |
| --- | --- |
| 图片视觉相似 | **可行**，建议做。Qt 原生即可实现，零新增依赖，包体不变 |
| 视频靠封面相似 | **否决**。三个致命问题 + 产品价值本身偏低，建议连实验开关都不做 |
| 是否必须给开关 | **必须**。而且要「开关 + 结果层兜底」双保险，不能只给一个开关 |
| 是否需要 Pillow | **不需要**。这是本方案相对旧 P3 计划的关键转折 |

---

## 一、背景：为什么现在重提这件事

旧的扩展计划里，图片相似去重被列为 **P3、暂缓**，卡点是：

> 「需引入 Pillow，约 +5MB 包体」

当时的判断是基于「算感知哈希要用图像库」。但现在重新审视后发现——

**Qt 原生就覆盖了全部所需运算，Pillow 根本不需要：**

| 需要的步骤 | PySide6 里的现成能力 |
| --- | --- |
| 解码并按尺寸降采样 | `QImageReader` + `setScaledSize()`（解码阶段就降采样，不读全图进内存） |
| 转灰度 | `QImage.convertToFormat(QImage.Format_Grayscale8)` |
| 缩到指纹尺寸 | `QImage.scaled(w, h, Qt.IgnoreAspectRatio)`（内部高质量重采样） |
| 读像素 | `QImage.constBits()` / `QImage.pixel()` |

再加上 **v3.28 已经落地的缩略图通路**（`core/thumbs.py`），素材其实是现成的。

---

## 二、视频为何被否决（重点）

### 2.1 原本的设想

上一轮规划里提过：视频/ PDF / Office 的封面可以由 `IShellItemImageFactory` 直接产出，
于是想到「给封面算同样的哈希，就能做相似视频」。**这个设想现在被推翻了。**

代码依据（`core/thumbs.py`）：

```python
VID_EXT = frozenset((".mp4", ".mkv", ".avi", ".mov", ".wmv", ".flv", ".webm",
                     ".m4v", ".mpg", ".mpeg", ".ts", ".rmvb", ".rm", ".3gp",
                     ".vob", ".m2ts"))
def wanted(path):        # 决定是否值得取缩略图
def _render_image(path, size):   # 图片走 QImageReader
def _shell_thumb(path, size):    # 视频等走 IShellItemImageFactory ← 取的是外壳默认封面
```

视频全部走 `_shell_thumb()`，Windows 返回的通常是**第一帧**（或外壳挑的代表帧，多数等于第一帧）。

### 2.2 问题一：第一帧黑屏 → 灾难级聚类

电影、屏幕录像、PR 渲染输出、大量压制片源，**开头几秒是纯黑或淡入**。

后果不是「偶尔误判几张」，而是：

- 这些帧缩到 16×16 灰度后，像素值几乎全部相同 → 哈希完全相同
- 硬盘上所有以黑屏开头的视频会被**聚成一个巨组**
- UI 会提示「发现 1 组相似视频，可释放 147 GB」，而实际内容毫不相干

这类误判是**成规模的、不可人工复核的**（一个组里几百个文件根本看不过来）。

### 2.3 问题二：共用片头 → 无关视频并成一组

同一 UP 主、同一套网课、同一部番剧、同一公司的宣传片，开头几秒完全一致。
封面取第一帧 ≈ 取到片头 → 全部归为一组，内容却完全不同。

### 2.4 问题三：跨封装封面不一致 → 反向漏判（既误判又漏判）

同一个视频的 `.mkv` 与 `.mp4` 两个副本，外壳调用**不同的解码器/渲染参数**，
产出的缩略图在尺寸、轻微色差上可能有差异 → 哈希距离被拉大。

结果是：**明明是同一个文件反倒判不出来**。一个算法同时具备「大规模误判」和「关键漏判」，不可用。

### 2.5 产品层面的判断：视频「疑似重复」本身价值低

这是比技术更重要的理由：

| 场景 | 用户的真实意图 |
| --- | --- |
| 图片：原图 + 压缩版 / 缩略图导出版 | 删掉压缩版**毫无损失**，价值明确 |
| 视频：720p + 1080p | 用户多半**两个都要**（手机看低的、电脑看高的），替他删哪个都不合适 |

而**完全相同的视频副本**（真正该清理的那部分），现有的 `MATCH_QUICK` / `MATCH_FULL`
（`core/dupfinder.py`）早就覆盖，`_hash()` 用的是首 64KB + 尾 64KB + 文件大小，或全量 md5。

**结论：视频场景中真正有价值的需求已经被满足，视觉相似只是「看起来很美」。**

### 2.6 唯一还算靠谱的替代：改用「时长」判定

跳过封面，改看元数据——同一视频的不同清晰度版本，**时长几乎完全一致**（差 <0.1 秒），
但字节数可能差 3 倍。这比封面可靠得多。

获取途径：Windows Property System（`SHGetPropertyStoreFromParsingName` + `PKEY_Media_Duration`），
走 ctypes，与 v3.28 已有的外壳通路同源。

**但仍建议不做**，理由：
1. 要新增一套 PropertyStore 的 COM 绑定，工作量不小、调试成本与收益不匹配
2. 判定出「疑似同一视频的不同版本」后，用户大概率**两个都不想删**（见 2.5）
3. 精确副本场景已被现有算法覆盖

> 若日后确实出现明确需求，可作为独立版本再做，不与 v3.31 混在一起。

## 三、图片为何可行

### 3.1 素材通路已就绪

`core/thumbs.py` 已有完整三通路，按代价递进：

1. `QImageReader`（图片，解码时即降采样）
2. `IShellItemImageFactory`（视频 / PDF / Office / 音频 / 压缩包）
3. `QFileIconProvider`（兜底）

且已有 `thumbs.db` 缓存：PNG BLOB，键 = 路径 + mtime + size，`MAX_ITEMS = 2000`，LRU 淘汰。

**这意味着算指纹时可以优先读缓存，避免重新解码几十 MB 的原图。**

### 3.2 Qt 原生覆盖全部运算，包体不变

见「一、背景」表格。全程只有 PySide6 + Python 标准库，**不引入任何第三方依赖**。

### 3.3 单一哈希不可靠，但多证据组合能压住误判

这是本方案的核心设计（详见第四节）：**不靠一个哈希定生死**，而是同时满足
「视觉距离 + 宽高比 + 色调分布」三重证据才判定相似。

## 四、算法设计（待细化）

### 4.1 指纹计算

```
原图 → QImageReader 降采样 → 转 Format_Grayscale8 → scaled(16, 16)
     → 读 256 个像素 → 算 dHash（主）+ aHash（辅）
```

参数选择理由：

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| 指纹尺寸 | **16×16 = 256 bit** | 常见的 8×8 = 64bit 信息量太小，随机碰撞率高；16×16 碰撞率显著下降，算力开销仍可忽略 |
| 主哈希 | **dHash**（相邻像素差值） | 对整体亮度偏移鲁棒（曝光不同的同一张图仍能匹配） |
| 辅哈希 | aHash（与均值比较） | 与 dHash 互补，降低纯色/渐变图的偶合概率 |
| 颜色 | 先转灰度 | 排除色彩配置差异带来的干扰 |

### 4.2 三重证据与阈值

判定「相似」需**同时**满足：

| 证据 | 判据 | 作用 |
| --- | --- | --- |
| ① 视觉距离 | dHash 汉明距离 ≤ 阈值 | 主判据 |
| ② 宽高比 | 两者宽高比差 ≤ 5% | 同一张图的缩放版必然同比；能砍掉大批「看着像其实比例不同」的误配 |
| ③ 色调分布 | 简化颜色直方图距离 ≤ 阈值 | 兜掉「结构相近但色调完全不像」的情况 |

阈值三档（**做成用户可调**，对应 `严格 / 标准 / 宽松`）：

| 档位 | 汉明距离（256bit） | 大约相似度 | 适用心态 |
| --- | --- | --- | --- |
| 严格 | ≤ 6 | ≈ 98% | 宁可漏，不可错 |
| 标准 | ≤ 12 | ≈ 95% | 默认档 |
| 宽松 | ≤ 20 | ≈ 92% | 想把「同一场景不同角度」也找出来 |

> 以上具体数值为标准库实现后的**实测标定项**，目前是估算起点。

### 4.3 聚类性能

朴素两两比对是 O(n²)：5000 张图 = 1250 万次比较。

优化手段：**先按宽高比分桶**（量化到 0.05 步长），只在「同桶 ±1」内两两比较。
这既大幅削减比较次数，语义上也正确（同一图的缩放版宽高比必然一致）。

单次比较用 `int.bit_count()`（C 实现），配合列表推导进一步提速。

兜底：参与文件数设上限（例如 5000），超出时提示用户缩小范围。

### 4.4 缓存设计：必须与 thumbs.db 分开

**不要复用 thumbs 缓存来存哈希**，原因：

- `MAX_ITEMS = 2000` 且是 LRU。扫 5000 张图时缓存反复淘汰，
  哈希所在的记录被挤掉后就要重新解码 → 反而更慢
- 预览图的淘汰策略（按最近使用）与指纹的需求（全量保留）不一致

方案：新建 `core/imghash.py` + **独立 SQLite 表**，字段大致为

```
path, mtime, size, dhash, ahash, aspect, hist, algo_version
```

只存哈希不存图：5000 条约 300 KB，极小。两张表互不干扰。

> `algo_version` 必须留：以后算法改了要让旧记录自动失效重算。

## 五、开关与安全设计（重点）

> 用户明确要求：**一定要有开关，让用户自己选择要不要做对比。**
> 但实际保护用户的不是开关本身，而是**结果层的兜底**。两层都要做。

### 5.1 UI 开关（去重页）

现有控件基础（`ui/dup_page.py`）：

```python
self.ck_thumb = QCheckBox("显示预览图")   # v3.28 已有，位于顶部 b2l 布局
```

建议新增一组「相似查找」控件：

| 控件 | 形式 | 选项/说明 |
| --- | --- | --- |
| 查找方式 | 下拉 | ① 完全相同的文件（默认，即现有行为）<br>② 内容相同的图片 ← 新增<br>**不提供视频选项**，避免误导 |
| 相似度 | 下拉/滑块 | 严格 / 标准 / 宽松，对应 4.2 的三档阈值 |
| 作用范围 | 隐含 | 只对 `IMG_EXT` 内的图片生效，用户无需理解 |

默认为「完全相同的文件」，即**不开启相似查找时，行为与现在完全一致**。

> ⚠️ 以上文案均为**方案草稿**，最终界面用词以用户确认为准，不擅自替换。

### 5.2 结果层的五条兜底（比开关更重要）

即使算法出错，也不能让用户的文件被误删：

1. **视觉区分「疑似」与「确认」**
   相似组在树中用不同图标/颜色标出「疑似」，与精确重复的「确认」组明确区分。

2. **相似组不参与自动挑选保留项**
   现有 `_auto_select()`（配合 `pick_keeper` 的 5 种保留规则）**只对精确重复组生效**，
   相似组保持全不勾选，必须用户手动点选。
   → 这一条是安全设计的核心。

3. **展示相似度百分比 + 并排对比**
   每组给出相似度数字，并提供双图并排查看，让用户能自己判断。

4. **提供「这组不是重复」忽略项**
   可整组忽略，或加入白名单，下次不再出现。

5. **统计文案分开报数**
   底部 `_update_stat()` 需区分输出。现文案为
   「已标记 N 个待删除 · 可释放 X · 共 G 组 / M 个文件」，
   相似模式下应改成类似「完全重复 G₁ 组 / 疑似相似 G₂ 组」的口径
   （最终文案待用户确认）。

## 六、风险清单

| 风险 | 说明 | 缓解措施 |
| --- | --- | --- |
| 纯色 / 渐变图误判 | 壁纸、背景图哈希易撞 | 三重证据 + 严格档阈值 + 默认不勾选 |
| 图标 / UI 截图 / 文字截图误判 | 信息熵低 | 同上；如需更稳可考虑允许排除这几类 |
| 阈值难以普适 | 「多像才算重复」是主观的 | 暴露三档给用户调，默认是中间档 |
| 大量文件性能 | 数千张图的聚类耗时 | 宽高比分桶 + 文件数上限保护 + 后台线程 |
| 缓存与算法升级 | 改算法后旧哈希失效 | 表内留 `algo_version`，版本不符自动重算 |
| heic/heif/avif 解码 | 依赖系统解码器支持 | 沿用 thumbs 已有降级逻辑，取不到就跳过 |

## 七、实施步骤（建议分阶段）

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| **S1 验证原型** | 脱离 UI，写个 `_` 前缀脚本：对一组真实图片算 dHash/aHash，<br>验证「原图 vs 微信压缩版」「连拍」「不同角度」「加了水印」等场景的命中情况 | 可行性实测数据 + 阈值标定 |
| **S2 内核落地** | `core/imghash.py`（指纹 + 独立缓存表 + 分桶聚类） | 可被冒烟测试调用 |
| **S3 界面接入** | 去重页加「相似查找」下拉 + 相似度档位；接入现有 ScanBanner | 开关可用 |
| **S4 结果层安全** | 相似组标记、不参与自动勾选、并排对比、忽略/白名单、统计口径 | 完整功能 |
| **S5 回归** | 跑 `smoke_test.py` + 离屏渲染对照，确认不影响现有精确去重 | 发版 |

每阶段结束跑一次 `tools/code_audit.py` 与冒烟测试。
