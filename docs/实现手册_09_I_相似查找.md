## 一、为什么要单列出来：这卷的数据我替你跑过了

与其抽象讨论，不如先看真实结果（512×512 的测试图，同一台机器跑的）：

| 变化 | 汉明距离 | 严格档（≤6）是否命中 |
| --- | --- | --- |
| **完全相同** | `0` | ✅ |
| **512 → 256 缩放** | `0` | ✅ |
| **JPEG 质量 35 重压缩**（模拟微信传过的图） | `3` | ✅ |
| **512 边缘裁掉 24px**（约 5%） | `16` | ❌ **漏判** |
| **完全不同的另一张图** | `19` | ✅（正确地没命中） |

三条结论，直接影响你后面的取舍：

1. **主力场景完全成立** —— 缩放、转发压缩、重复下载，这些都能抓到。
2. **裁剪是硬伤，而且比想象中敏感** —— 只裁掉 5% 的边缘，距离就从 0 跳到 16。
   原因是 dHash 做的是「相邻像素差分」，裁一点边，整行的对应关系就整体错位了。
   ⚠️ **这一点必须让用户知道**，否则他会以为「明明是同一张图怎么找不到」。
   UI 文案里要写明（见第六节）。
3. **不会误判** —— 无关图距离 19，离任何一档阈值都很远。这是「可以放心给默认严格」的依据。

## 二、红线例外：这里允许 core 层 import Qt

总纲红线 4 写着「core 层不许 import PySide6」。**`core/imghash.py` 是唯一登记在案的例外。**

```python
from PySide6.QtCore import QSize
from PySide6.QtGui import QImage, QImageReader
```

**理由**：算感知哈希要先把 JPEG / PNG 解码并缩到 9×8 灰度。
Qt 自带的 `QImage` 是唯一不引入第三方依赖的解码方案 ——
用 Pillow 就要多背 5 MB 左右的包体（这是旧 P3 计划当年搁置的原因，现在已经不需要了）。

**边界（必须守住，否则例外作废）**：

- ❌ 不许 import `QtWidgets` / 任何控件类
- ❌ 不许创建 `QApplication` / `QGuiApplication` / 任何窗口
- ✅ 只把 Qt 当「图像解码器」用
- ✅ 只在界面进程的后台线程里被调用

> 如果后续有人要给「相似查找」加交互，那部分代码必须放 `ui/`，不许塞进这个文件。

### 3.2 三个容易写错的实现细节

**① `setAutoTransform(True)` —— 漏了会全错**

```python
rd = QImageReader(path)
rd.setAutoTransform(True)          # ← 手机竖拍照片带 EXIF 旋转标记
rd.setScaledSize(QSize(9, 8))      # ← 解码时就降采样，不必把原图整个读进来
```

同一张竖拍照片，系统里存的方向和实际显示方向可能差 90°。
不看 EXIF，缩略图和原图的哈希会差得离谱 —— **这是相机照片最大的坑**。

**② `bytesPerLine()` 才是行步长，不是图像宽度**

Qt 的行是按字节对齐的（通常 4 字节），9 像素宽的灰度图每行可能占 12 字节。
用 `w` 当步长索引像素，出来的就是错位的哈希，而且症状很隐蔽（一半的图还能分组）。

```python
stride = int(img.bytesPerLine())
raw = img.constBits()
if isinstance(raw, memoryview):
    raw = raw.tobytes()
for y in range(8):
    row = raw[y * stride: y * stride + 9]
```

**③ 聚类必须先「位切片」筛选，不能直接 O(n²) 两两比**

5000 张图两两比是 1250 万次 —— 界面会卡成幻灯片。
做法是把 64 位哈希切成 4 段 16 位，**只有至少一段完全相同才成为候选对**：

```python
def _segments(h):
    return [(h >> 48) & 0xFFFF, (h >> 32) & 0xFFFF,
            (h >> 16) & 0xFFFF, h & 0xFFFF]
```

再对候选对做并查集合并。实测 5 张图跑出：

```
组: ['orig.png', 'resized.png', 'jpg_compressed.jpg']
```

（不同图的 `different.png`、被漏判的 `cropped.png` 各自落单 —— 与距离表一致。）

> 另外加了 `len(idxs) > 400` 的保护：纯色图会让某个段值极其常见，
> 不跳过的话这一段会自己炸出大量候选对。

### S3 · 接进扫描流程（两阶段）

`core/dupfinder.py` 现有结构：

```python
MATCH_SIZE = 0
MATCH_QUICK = 1
MATCH_FULL = 2

    "仅按大小（最快，可能误判）",
    "大小 + 快速校验（推荐）",
    "大小 + 完整 MD5（最准，慢）",

```

**新增**：

```python
MATCH_SIMILAR = 3
MATCH_LABELS = [
    "仅按大小（最快，可能误判）",
    "大小 + 快速校验（推荐）",
    "大小 + 完整 MD5（最准，慢）",
    "相似查找（仅图片，看内容）",
]
```

⚠️ **加在末尾，不要插在中间** —— 这个值会写进用户配置（`dup_match`），
插队会让老用户的"完整 MD5"突然变成别的意思。

产出的组结构要与现有保持一致，这样 UI 几乎不用改：

```python
{"size": <单份大小>, "hash": "<hex>", "files": [{"path","size","mtime","ctime"}, ...], "waste": <可释放>}
```

🔴 **但「可释放」的算法对相似组必须是另一套 —— 这是最容易漏的一处**：

现有逻辑（精确重复）假设组内每个文件大小都一样：

```python
g["waste"] = g["size"] * (len(g["files"]) - 1)
```

**相似组内每张图大小不同**，直接套这个公式会算出离谱的数字。
正确做法是把 **最大那份当作保留对象**，其余算冗余：

```python
sizes = sorted(f["size"] for f in files)
size = sizes[-1]                          # 每份的标称大小 = 最大的那份
waste = sum(sizes) - size                 # 其余都算冗余
```

并且 `ui/dup_page.py` 里有两处会按老公式重算，**必须一并改**：

- 约 953 行 `_waste_total()`
- 约 978 行 `n_del` 那条 `g['size'] * n_del`

判断方式建议给组加一个标记 `g["kind"] = "similar"`，这两处按它分支。

### S5 · 五条兜底（这才是真正保护用户的东西）

用户说过「一定要添加开关」——但**光有开关不够**。
详细的五条设计见 `扩展计划_相似图片去重.md` 第五节，这里只列接入点：

| # | 兜底 | 接入点 |
| --- | --- | --- |
| 1 | **相似组不参与自动挑选保留项** | `_auto_select()`：只对 `kind != "similar"` 的组生效 |
| 2 | 疑似 / 确认视觉区分 | 相似组的行加一圈虚线边框或浅底色，标题写「疑似相似」 |
| 3 | 显示相似度百分比 + 并排对比 | 详情面板复用 v3.28 的 `_show_detail_thumb` 通路 |
| 4 | 「这组不是重复」整组忽略 | 右键菜单加一项，记进 `cfg["sim_ignored"]` |
| 5 | 底部统计分开报数 | `_update_stat()`：`精确 N 组 · 疑似相似 M 组 · 可释放 X` |

🔴 **第 1 条是底线**：现有 `_auto_select()` 只对精确重复生效，相似组必须保持**全不勾选**。
这样即便算法抽风，它也只是在用户眼前提了个可能不对的建议，不会替他删掉任何东西。

## 八、常见错误

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `ModuleNotFoundError: PySide6` | 用了 managed Python | 换 venv 里的 python.exe |
| 同一张横拍/竖拍图距离很远 | 没设 `setAutoTransform` | 必须 `rd.setAutoTransform(True)` |
| 哈希看着随机、图谱乱七八糟 | 用图像宽度当行步长 | 用 `img.bytesPerLine()` |
| 五千张图卡死 | 直连 O(n²) 两两比 | `group_similar` 的位切片分桶不能省 |
| 「可释放」大得离谱 | 用了 `size × (n-1)` | 相似组改 `sum - max` |
| 系统墙纸照样进组 | 路径没归一化 | `\` 归一化 + 折叠连续分隔符 |
| 老用户设置的"完整 MD5"变成相似查找 | 往 `MATCH_LABELS` 中间插队 | **只能加在末尾** |
| 用户的图被自动勾上了 | `_auto_select` 没排除相似组 | 第 1 条兜底，必做 |
| 用户抱怨"明显一样的图找不到" | 裁过一点点 / 旋转过 | 引导切宽松档；并认这是 dHash 的固有局限 |
